## ✅ **인증 흐름 전체 요약 (httpOnly 쿠키 + Next 서버 → 백엔드 Authorization 변환)**

### 1. **로그인**

- 클라이언트가 로그인 요청을 `Next.js API Route (/api/auth/login)`로 보냄
- Next 서버는 백엔드에 로그인 요청 → **JWT를 JSON body로 응답받음**
- Next 서버가 JWT를 **httpOnly 쿠키로 설정하여 클라이언트에 반환**

> 🔐 클라이언트는 JS로 토큰을 다루지 않고, 쿠키만 보관

---

### 2. **인증된 API 요청**

- 클라이언트가 Next.js의 API Route로 요청 시, 브라우저가 자동으로 쿠키 전송
- Next API Route는 쿠키에서 JWT를 읽어 **Authorization 헤더로 변환**
- 백엔드에 요청 시 `Authorization: Bearer <JWT>`로 전달

> 🔁 이 과정을 모든 API 라우트에서 **공통 유틸**로 처리 (중복 없음)

---

### 3. **로그인 상태 확인**

- 클라이언트는 자체 상태(zustand 등)로 `isLoggedIn` 관리
- SSR 환경에서는 `layout.tsx`에서 `cookies()`로 쿠키 유무 확인
- `/auth/me` 같은 인증 확인 API는 **추후 필요시 도입 가능** (지금은 생략)

---

### 4. **로그아웃**

- 클라이언트가 `/api/auth/logout`으로 요청
- Next 서버는 **JWT 쿠키를 만료시킴** (`Set-Cookie: Max-Age=0`)
- 클라이언트 상태 초기화 (로그인 상태 false)

## 📌 핵심 개념 요약

| 항목             | 방식                                              | 비고                    |
| ---------------- | ------------------------------------------------- | ----------------------- |
| 토큰 저장        | httpOnly 쿠키                                     | JS 접근 불가, 보안 강화 |
| 백엔드 인증 전달 | Next 서버가 쿠키 → 헤더로 변환                    | 공통 fetch 래퍼 사용    |
| 로그인 유지      | 브라우저 쿠키 기반                                | 새로고침/재접속 시 유지 |
| 로그아웃 처리    | 쿠키 만료 (`Set-Cookie`)                          | 상태 초기화 동반        |
| 구조 변경 대응   | 쿠키 기반 인증으로 변경 시 `fetch wrapper`만 수정 | 유지보수 효율 ↑         |

## ✅ 유지 목적

- **보안성 확보** (httpOnly)
- **중앙 집중 처리** (fetch proxy 유틸로 통합)
- **향후 유연한 확장 가능성** 확보 (예: `/auth/me`, 쿠키 인증 전환 등)
